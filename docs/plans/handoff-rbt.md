## What landed

- **Rust bench twin** `bench-engine/src/structures/rbt.rs` (`RbtF64`): classic CLRS red-black
  multiset. Arena with slot 0 as a never-written NIL sentinel, parent links, free-list slot reuse
  (a churn pair allocates nothing in steady state), every walk iterative. Value-copy (Hibbard)
  delete over the CLRS delete fix-up, with the fix-up's parent carried explicitly rather than
  parked in `nil.p`. Counted path returns a `Cost { comparisons, rotations, recolours }`; the
  shared metric is `comparisons + rotations`, exactly the AVL's. Same `#[wasm_bindgen]` harness
  surface as `AvlF64` (two-key churn, alternating teardown).
- **Unit tests** in `rbt.rs`: every insert fix-up case and every delete fix-up case with
  hand-computed counts/shapes; a test that `check_rb` catches each invariant it claims;
  **value-copy delete ≡ CLRS RB-TRANSPLANT delete** (a test-only transplant implementation,
  40 random distinct-key rounds, shape+colour identical after every delete); rotation budget
  (≤ 2 per insert, ≤ 3 per delete) over a long mixed sequence; arena reuse under churn.
- **Proptest** `bench-engine/tests/proptest_rbt.rs`: bulk build and mixed insert/delete streams
  against a `BTreeMap<key, multiplicity>` multiset reference; after **every** op: in-order ==
  sorted multiset, `len`, `check_rb()` (black root, no red-red, equal black heights, parent
  links, reachable count, height ≤ 2·log₂(n+1)), **and the rotation budget**.
- **Corpus** `conformance/corpus-rbt.txt`, generated by `bench-engine/src/structures/conformance_rbt.rs`
  (own file, declared next to `mod conformance;` in `mod.rs`): 15 cases. Columns beyond the AVL
  corpus: per-insert op-counts during the build, **shape with colours** (`40b 20r . .`), and
  build/delete **rotation and recolour totals**. A guard test asserts the cases reach inserts
  with 0/1/2 rotations and deletes with 0/1/2/3.
- **TS teaching twin** `src/structures/rbt.ts` (+ `rbt.test.ts`, `conformance-rbt.test.ts`):
  object nodes with parent links, same algorithm and counting; reproduces the corpus on every
  column first time. No tracer/animation (later round).
- **Clock-free methodology** — five tests appended to `structures::methodology` in `mod.rs`.
- **Wiring**: `'rbt'` in `StructureId`, registry entry + `STRUCTURES`, search sweep (7th search

## The finding (what the op-counts actually say — narrower than the slogan)

Measured at n = 4000, same key sequences for both trees. AVL comparisons/rotations are split
without touching `avl.rs`: for distinct keys an insert descends exactly the path a failed
search takes in the pre-insert tree, and a delete's find stops where search stops, so
`rotations = op-count − search_one_counted(key)` with the search taken first.

| sequence | AVL cmp / rot | RB cmp / rot / recolours | reading |
|---|---|---|---|
| shuffled build | 43 069 / 2830 | 43 122 / 2311 / 9223 | RB **~18 % fewer rotations** (0.58 vs 0.71 per insert), comparisons equal (+0.1 %), but **4× as many recolours as rotations** |
| ascending build | 43 905 / 3988 | 73 809 / 3979 / 19 891 | rotations **equal** (≈ 1 per insert both); RB **+68 % comparisons** — sorted keys keep landing on its deep spine |
| shuffled alternating teardown | 37 406 / 2761, **max 10 per delete** | 33 194 / 2690, **max 3** | totals ≈ equal; the **per-op bound** is the real difference |
| random-order delete (shuffled) | 39 192 / 1466, max 6 | 39 187 / 1501, max 3 | RB totals slightly *higher* (+2.4 %) |
| heights (shuffled / ascending) | 15 / 12 | 15 / 21 (bound 23.9) | IPL within 0.4 % / 3.8 % — the finished sorted RB tree is nearly as good to *search* |
| churn vs FD (shuffled) | churn 26, sum 23.33 (10 %) | churn 27, sum 22.21 (~18 %) | tenth regime: AVL's direction, wider |
| reverse-sorted search-min / churn | 11 / 23 | 19 / 30 | BST: 2000 / O(n) |

So: **"fewer rotations" is a bound on the worst single operation (RB ≤ 2 / ≤ 3, the AVL was seen
at 10 on one delete) plus a ~18 % total saving on random inserts — not a property of every
total.** On sorted inserts and on deletes the totals are a wash. "Slightly more comparisons"
holds on shuffled data as "the same", and on sorted input as "68 % more for the build", because
the looser bound shows up exactly on the spine sorted input inserts down — though the average
search cost of the finished tree is only ~4 % higher. And the RB tree recolours far more than
it rotates, which the shared metric deliberately does not charge.

### New §2.9 (after §2.8 if another slice adds one, else after §2.7)

> ### 2.9 Two balancing schemes, one metric (the red-black tree)
>
> The red-black tree is here to answer one question (PLAN §13): what does a *balancing scheme*
> cost? The AVL keeps every node's subtrees within one level of each other, so its height is
> ≤ ≈1.44·log₂ n — but a delete may have to rebalance at every level on the way back up. A
> red-black tree promises only that no root-to-leaf path is more than twice another (height
> ≤ 2·log₂(n+1)), and in exchange **never rotates more than twice on an insert or three times
> on a delete**. Ours is classic CLRS on the AVL's exact semantics (multiset, equal keys right,
> value-copy delete) and the AVL's exact metric — comparisons + rotations — so the two curves
> differ only by the scheme.
>
> **What the metric leaves out, on purpose.** Where the AVL rotates, a red-black tree mostly
> *recolours*, and a recolour can walk O(log n) levels up. The AVL has no colour, so charging
> recolours would put a cost on the chart only one line can pay; they are counted on a separate
> counter instead (a recolour = a write that changes a node's colour) and reported here, so
> "fewer rotations" is never read as "less work".
>
> **What the op-counts say** (n = 4000, the same key sequences for both trees; the AVL's
> comparisons and rotations are separated by subtracting a pre-op search count, valid for
> distinct keys):
>
> | | AVL | red-black |
> |---|---|---|
> | rotations, shuffled build | 2830 (0.71 / insert) | **2311 (0.58 / insert)** |
> | rotations, ascending build | 3988 | 3979 |
> | rotations, shuffled teardown / random-order delete | 2761 / 1466 | 2690 / 1501 |
> | **most rotations in one delete** | **10** (teardown), 6 (random order) | **3** (the bound) |
> | recolours, shuffled build | — | 9223 (4× its rotations) |
> | comparisons, shuffled build | 43 069 | 43 122 |
> | comparisons, ascending build | 43 905 | **73 809** |
> | height, shuffled / ascending | 15 / 12 | 15 / **21** (bound 23.9) |
> | average search (IPL), ascending | 43 917 | 45 586 (+3.8 %) |
>
> Three readings, each pinned by a test:
>
> 1. **The guarantee is per operation.** On every insert and delete of every sequence, and after
>    every operation of the proptest, the red-black tree stays within 2 / 3 rotations; the AVL
>    exceeded 3 on a single delete of the same teardown. That is the scheme's real advantage —
>    and it is a statement about the *worst single operation*, which no per-op average on the
>    Compare chart can show.
> 2. **In totals the saving is narrow.** ~18 % fewer rotations on random inserts; the same on
>    sorted inserts (about one per insert, both); a wash on deletes, the red-black tree's
>    slightly higher.
> 3. **The looser bound costs comparisons where sorted input inserts.** On shuffled keys both
>    trees end up the same height and search the same. On sorted keys the AVL builds a
>    near-perfect tree while the red-black tree's *edges* grow toward its 2·log₂ n bound — and
>    the edge is exactly where every sorted insert lands, so the sorted build costs 68 % more
>    comparisons even though the finished tree's average search is only ~4 % dearer. Its churn
>    (which rides the edges) sits above the AVL's on sorted input too. A constant, not a class.
>
> The churn-vs-finite-difference regime (§2.3, the tenth) follows the AVL's direction and is
> wider for reason 3.
>
> **Every number above is an op-count, and that is the only signal on which the RB-vs-AVL gap
> is "the scheme and nothing else".** The two twins store their nodes differently — the AVL is a
> recursive `Box` tree that allocates and frees a node on every churn pair and every build key;
> the red-black tree is a pre-sized arena that reuses freed slots — so on the wall clock the gap
> between their lines also carries allocator and memory-layout effects, and the red-black churn
> line can sit *below* the AVL's while doing more comparisons. Read the two wall-clock lines for
> shape; read the op-count lines for the scheme.

## (4) CLAUDE.md gotchas

> - **The red-black tree's metric is the AVL's on purpose — recolours are counted but not
>   charged.** `rbt.rs` returns `Cost { comparisons, rotations, recolours }` and the shared
>   op-count is `comparisons + rotations` only, so the two balanced trees compare unit for unit
>   (the AVL has no colour to pay for). Don't fold recolours into `ops` to "be complete", and
>   don't drop the counter: METHODOLOGY §2.9 reports them so "fewer rotations" is never read as
>   "less work". A recolour is a write that *changes* a colour (a new node born red is not one; a
>   node that goes red then black counts twice) — the TS twin and the corpus's `rbt_recolours`
>   column depend on that exact rule.
> - **The RB tree's NIL sentinel is never written.** Slot 0 is black forever; the delete fix-up
>   carries `x`'s parent (`xp`) and side (`x_is_left`) explicitly instead of the CLRS trick of
>   parking it in `nil.p`. Don't "simplify" back to CLRS's form — in an arena it aliases every
>   absent child, and the TS twin (which uses `null`) could no longer mirror it.
> - **"Fewer rotations" is a per-operation bound, not a total.** The methodology tests pin what the
>   op-counts say: ≤ 2 / ≤ 3 per op for RB vs an AVL delete at 10, but totals only ~18 % lower on
>   random inserts and a wash elsewhere; and on *sorted* input the RB tree's churn sits *above*
>   the AVL's (deeper spines). That is the finding, not a regression — don't add a gate check
>   asserting the RB line below the AVL's.
> - **RB vs AVL is a scheme comparison on op-counts only.** The AVL is a recursive `Box` tree that
>   allocates a node per insert; the RB tree is a pre-sized arena that reuses slots. So the
>   wall-clock gap between their lines includes allocator/layout effects (RB churn can read
>   *faster* while doing more comparisons). Keep every "RB above/below AVL" sentence on the page
>   qualified by signal (`CompareSection.tsx`'s sorted note is), and don't "fix" it by moving the
>   AVL onto an arena without re-pinning its corpus and methodology numbers.
> - **Splitting the AVL's op-count needs distinct keys.** The methodology tests derive AVL
>   rotations as `op-count − search_one_counted(key)` taken just before the op; that identity
>   holds only when the key is distinct (insert) or the first match is the one search finds
>   (delete). Keep those sequences permutations.

### Judgement calls a reviewer may disagree with

1. **The RB tree is on the search chart, the AVL is not.** The brief asked for search wiring; the
   AVL (and BST) were never in `runSweep`. So the search chart has one tree, and the RB-vs-AVL
   *search* comparison is clock-free only. Adding the AVL to `runSweep` is a one-liner but changes
   other slices' counts; left as a follow-up.
2. **Recolours outside the shared metric** (counted separately, in the corpus and §2.9). The
   alternative — charging them — makes the RB line incomparable with the AVL's.
3. **Recolour definition** = a write that changes a colour; a node born red is free; red-then-black
   in one fix-up counts 2. Mechanical and unambiguous, but it is a definition.
4. **Value-copy delete** (as the AVL/BST) rather than CLRS's node-moving transplant — proven
   equivalent in shape and colour by a unit test; recolour counts differ from a transplant
   implementation only in that value-copy never "copies z's colour onto y" (no such write exists).
5. **Arena + parent links, not the AVL's recursive `Box`** — per the brief; the height bound would
   have made recursion safe. Insert/delete/traversals are all loops; `check_rb` is iterative too.
   `RbtF64::new` pre-sizes the arena (one allocation per build; the AVL allocates one Box per key).
   **Consequence for reading the charts:** on the wall clock the RB-vs-AVL gap is not purely the
   scheme — it also carries this storage difference (the AVL's churn pair allocates and frees a
   node; the RB pair reuses a slot). The page copy, the worker JSDoc and the registry doc now say
   the "gap = scheme" reading holds on op-counts only; §2.9 and hurdle 13 above carry the caveat.
6. **AVL rotation split by subtraction** (op-count − pre-op search count, distinct keys) instead
   of adding a rotation counter to `avl.rs`. Avoided editing the sibling; valid only for distinct
   keys, which every methodology sequence is.
7. **Gate asserts class only** for the RB tree (sub-linear search and churn on both passes). No
   "RB below AVL" or "RB above AVL" constant check — the op-counts say the order flips with input
   order, and the clock is too noisy for constant gaps.
8. **The AVL's "10 rotations in one delete"** is an observation on one fixed shuffled sequence, asserted
   as `> 3` (deterministic, so it cannot flake, but it is a property of that sequence, not a
   theorem about AVL trees in general — the theorem is that it *can* be O(log n)).
9. **Teardown comparisons favour the RB tree on shuffled data** (33 194 vs 37 406) — measured,
   not asserted, not written into §2.9; worth a look if someone wants a fuller delete story.
10. **Gate first-pass timeout 90 s → 120 s** — a change to an existing line, made because one
    more sweep runs before the done-signal.
